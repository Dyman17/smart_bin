# HerbiBioS — единый справочник проекта

Этот файл — главное описание финального комплекта: что уже работает, как проект должен быть устроен, какие классы распознаются, как предполагается связать ноутбук, ESP32-CAM и три сервопривода, а также что ещё нужно уточнить и проверить. Значения, которых пока никто не измерял или не подтвердил, помечены как **TBD**.

## Быстрый запуск после скачивания ZIP

В ZIP должны быть файлы прошивки, приложение и обе модели в `models/`. Датасет и временные файлы Python не нужны.

1. **Прошейте ESP32-CAM.** В Arduino IDE установите пакет плат Espressif ESP32 и библиотеку `ESP32Servo`. Откройте `esp32_cam/HerbiBioS/HerbiBioS.ino`, выберите **AI Thinker ESP32-CAM** и COM-порт адаптера, загрузите скетч. Во время загрузки IO0 должен быть соединён с GND; после прошивки отключите IO0 от GND и перезапустите плату. Подробности и важные предупреждения по подключению — в [`esp32_cam/README.md`](esp32_cam/README.md).
2. **Подключите ноутбук к Wi-Fi платы:** `Garbage`, пароль `12345678`. Проверьте в браузере `http://192.168.4.1/health` и `http://192.168.4.1/capture`.
3. **Установите и запустите панель** в PowerShell из папки `laptop_ai`:

   ```powershell
   python -m pip install -r requirements.txt
   python control_panel.py
   ```

   Откройте `http://127.0.0.1:5000`. Веса уже лежат в `models/`; приложение разрешает их относительные пути автоматически.
4. **Начните с безопасного режима.** Физическое управление по умолчанию выключено (`actuation_enabled: false`, Serial отключён). Для управления реальными приводами после проверки распиновки, питания, безопасных углов и COM-порта измените параметры `project.actuation_enabled`, `serial.enabled`, `serial.dry_run` и `serial.port` в `laptop_ai/config.yaml`. Закройте Serial Monitor Arduino IDE перед запуском панели.

Проектные тесты ноутбучной части запускаются из `laptop_ai`: `python -m pytest -q`.

**Важно:** файлы позволяют собрать и запустить программные части, но прошивка и аппаратная цепочка не проверялись на целевой физической плате. Распиновку камеры, уровни UART, питание и углы сервоприводов необходимо проверить на реальном устройстве; до этого не включайте физическое управление.

## 1. Идея проекта

Физический макет имеет три отсека. ESP32-CAM фотографирует поданный предмет и отправляет изображение ноутбуку по локальному Wi-Fi. На ноутбуке запускается обученная модель YOLOv8s, которая обнаруживает и классифицирует мусор. Если класс известен, уверенность достаточная и решение однозначно соответствует одному из трёх отсеков, ноутбук отправляет ESP32-CAM логическую команду через USB-UART/Serial. ESP32-CAM выбирает подключённый к соответствующему GPIO сервопривод, открывает нужный отсек примерно на 3 секунды, затем закрывает его. Сервоприводы работают **по очереди**, не одновременно. Неизвестный предмет, лицо, недостаточная уверенность или ошибка связи не должны вызывать движение.

Роли компонентов:

- **ESP32-CAM + OV3660:** раздаёт Wi-Fi AP `Garbage`, фотографирует по запросу ноутбука, получает Serial-команду и управляет серво.
- **Ноутбук:** приём фото, инференс на YOLO, фильтрация лиц и низкой уверенности, выбор корзины, отправка команды через USB-UART.
- **USB-UART:** Serial-мост между ноутбуком и ESP32-CAM; адаптер обозначен как USB TO TTL MH, уровни UART пока неизвестны.
- **Breadboard:** макетирование общих соединений; фактический допустимый ток её дорожек/контактов нужно учитывать.
- **Три TowerPro MG90S:** механическое открытие отсеков по одному.

## 3. Что распознаёт ИИ

Модель мусора обучена на предоставленном датасете и выдаёт 10 классов:

| ID | Класс модели | Текущий результат сортировки |
|---:|---|---|
| 0 | battery | UNKNOWN — не отправлять команду |
| 1 | can | BIN_2 |
| 2 | cardboard | BIN_3 |
| 3 | drink carton | BIN_1 |
| 4 | glass bottle | UNKNOWN — не отправлять команду |
| 5 | paper | BIN_3 |
| 6 | plastic bag | BIN_1 |
| 7 | plastic bottle | BIN_1 |
| 8 | plastic bottle cap | BIN_1 |
| 9 | pop tab | BIN_2 |

Это **10 классов модели**, сведённых в **3 отсека**:

1. **BIN_1 — пластик и упаковка:** plastic bottle, plastic bag, plastic bottle cap, drink carton.
2. **BIN_2 — металл:** can, pop tab.
3. **BIN_3 — бумага и картон:** paper, cardboard.

`battery` и `glass bottle` не назначены отсеку и должны оставаться `UNKNOWN`. Не следует угадывать материал предмета: модель классифицирует видимые категории датасета, а не гарантированно определяет состав материала.

Отдельно используется модель YOLOv8n-face. Она служит только для подавления ложных детекций, связанных с лицами: лицо **не является классом мусора**, не имеет BIN и не должно вызывать сортировку. Лицевые рамки в превью показываются отдельно. Детекции ниже порога уверенности **0.55 (55%)** не показываются; для безопасной сортировки недостаточно одного только отображения — решение также должно пройти mapping и safety-проверки.

Mapping и ID классов заданы в `ai_classes/classes.yaml`; runtime mapping также находится в `laptop_ai/config.yaml`. При изменении одного обновляйте другой.

## 4. Состояние моделей и проверки

- Модель мусора: YOLOv8s, дообученная на предоставленном Roboflow-датасете.
- Итоговые веса модели мусора: `models/waste_yolov8s_best.pt`.
- Детектор лиц: `models/yolov8n-face.pt`.
- Dataset: train — 5 220 изображений; valid — 435 изображений; отдельного test split нет.
- Validation-метрики обучения: precision 0.943, recall 0.937, mAP50 0.970, mAP50-95 0.819.
- Дообученная модель проверена на validation-примерах; в исходной части проекта прошли 6 тестов, в final-product ноутбучной части — 8 тестов.
- Live inference с веб-камерой ноутбука запускался.
- код точки доступа, HTTP capture endpoint, обработчика Serial-команд, последовательного servo state machine и веб-панели добавлен; физическая работа камеры, Wi-Fi, UART и серво ещё не подтверждена end-to-end.

Метрики относятся к validation, а не к отдельному независимому test-набору и не гарантируют точность на реальных снимках макета. Перед автоматизацией проверьте свои предметы, фон, расстояние, освещение и положение камеры.

## 5. Предлагаемый поток данных и действий

1. ESP32-CAM создаёт Wi-Fi точку доступа `Garbage`; ноутбук подключается к ней.
2. Ноутбук запрашивает один JPEG с `http://192.168.4.1/capture`; отдельный снимок используется как событие, а не непрерывный видеопоток.
3. Python-приложение ноутбука декодирует JPEG и выполняет inference обеими моделями.
4. Приложение отбрасывает детекции ниже 0.55, пропускает лицо/перекрывающийся с лицом мусор, выбирает корректный объект и вычисляет BIN.
5. Если решение `UNKNOWN`, пустое или неоднозначное — не отправлять команду сортировки.
6. Если команда валидна и контроллер не занят, ноутбук отправляет одну строку `BIN_1\n`, `BIN_2\n` или `BIN_3\n` через Serial.
7. ESP32 проверяет команду по белому списку и сопоставляет логический BIN локальному GPIO. Не принимать произвольное GPIO-число от ноутбука.
8. ESP32 открывает один отсек, держит его открытым примерно 3 секунды, закрывает, после чего снова принимает новую команду.
9. ESP32 отвечает по Serial `ACK`, затем после закрытия отсека `DONE`; при занятом приводе отвечает `BUSY`.

### Защита от повторных срабатываний

- Одно принятое фото считается одним событием распознавания.
- Одна команда на один объект/событие; один кадр не должен генерировать серию одинаковых команд.
- Во время 3-секундного цикла серво контроллер занят: новую команду безопаснее отклонить с `BUSY`, а не выполнять параллельно. Очередь можно добавить позже, если она действительно нужна.
- Сначала завершить цикл текущего серво и вернуть его в закрытое положение, только затем принять следующую команду.
- При потере Wi-Fi/Serial, ошибке inference, малой уверенности или UNKNOWN не двигать серво.
- После сброса/перезапуска серво должны перейти в заранее проверенное безопасное состояние; конкретный метод и положение TBD.

## 6. Предлагаемый Serial-протокол

Python `SerialController` и скетч используют текстовые команды с newline:

```text
Ноутбук -> ESP32: BIN_1\n
Ноутбук -> ESP32: BIN_2\n
Ноутбук -> ESP32: BIN_3\n
```

`UNKNOWN` может использоваться только как диагностическое сообщение; предпочтительно вообще не отправлять его как команду движения. ESP32 принимает только три разрешённые команды, остальное игнорирует/отвечает ошибкой. Физические GPIO остаются в конфигурации прошивки.

Для автоматического цикла ответы ESP32:

```text
ACK BIN_1\n
BUSY\n
ERR UNKNOWN_COMMAND\n
DONE BIN_1\n
```

Для ручной калибровки сайта доступны команды `MOVE BIN_n angle`, `SET BIN_n OPEN angle`, `SET BIN_n CLOSED angle`, `GET_ANGLES`. Все значения угла ограничены диапазоном 0–180; сохранённые OPEN/CLOSED углы хранятся в NVS ESP32 и переживают перезапуск. MANUAL/AUTO — режимы приложения на ноутбуке; скетч принимает только явные команды и не переключает режим самостоятельно. Скорость UART — 115200. Для первой отладки оставьте физическое управление выключенным.

## 7. Плата, GPIO и подключения

Известно со слов владельца:

- на модуле камеры написано OV3660;
- на основной плате указано `ESP-32S`;
- USB-UART адаптер имеет контакты `5V`, `VCC`, `3V3`, `TXD`, `RXD`, `GND`;
- подключены/планируются три TowerPro MG90S;
- PWM-драйвер добавлять пока не планируется; предпочтение — прямые GPIO;
- пользователь уже использовал 5V/GND USB-UART через breadboard, и этот вариант работал;
- серво должны работать по одному, не одновременно;
- SD-карта использоваться не будет; старый рабочий sketch использует `CAMERA_MODEL_AI_THINKER`.

Для выбранной распиновки принята AI-Thinker-совместимая камера из старого рабочего sketch. Серво назначены GPIO12, GPIO13 и GPIO14; microSD не используется, GPIO4 оставлен вспышке. GPIO12 — boot-strapping pin: проверь повторную загрузку платы с подключённым сигналом серво. Если загрузка нестабильна, отключи питание и перенеси BIN_1 обратно на GPIO4.

| Функция | Физический GPIO | Статус |
|---|---|---|
| Сигнал серво BIN_1 | GPIO12 / IO12 | Boot-strapping pin; проверить старт с подключённым сигналом |
| Сигнал серво BIN_2 | GPIO13 / IO13 | SD не используется |
| Сигнал серво BIN_3 | GPIO14 / IO14 | SD не используется |
| USB-UART TXD → ESP32 RX | U0R / UART0 RX | Перекрёстное подключение |
| ESP32 TX → USB-UART RXD | U0T / UART0 TX | Перекрёстное подключение |
| Камера OV3660 | AI-Thinker map в `esp32_cam/HerbiBioS/camera_pins.h` | По старому рабочему sketch |

Перед физическим включением проверить:

- что выбранный AI-Thinker camera pin map совпадает с этой платой;
- что USB-UART TX/RX уровни совместимы с 3.3V ESP32;
- что сервосигналы на GPIO12/13/14 не мешают запуску платы или камере;
- ограничения PWM/LEDC выбранных версий Arduino ESP32 core и ESP32Servo;
- поведение платы при старте и reset.

UART адаптер нужно подключать перекрёстно: адаптер TXD → ESP32 RX, адаптер RXD → ESP32 TX, GND ↔ GND. Линия питания подключается отдельно по выбранной схеме. Надпись `5V` на плате адаптера не говорит, что TXD/RXD являются 5-вольтовой логикой; проверить модель адаптера и уровни. ESP32 работает с логическими уровнями 3.3V; не подавать 5V logic на GPIO.

## 8. Питание и последовательная работа MG90S

Пользователь сообщил, что его прежняя схема с питанием через 5V/GND USB-UART и breadboard работала. В проекте серво не включаются одновременно: в один момент работает максимум один привод, и это уменьшает пиковую нагрузку относительно трёх одновременных движений. Это принято как факт уже опробованного владельцем setup; окончательная пригодность конкретного адаптера/проводов для текущей сборки всё же зависит от реального числа подключённых серво, их нагрузки и поведения при упоре.

Базовые принципы подключения:

- GPIO несёт только сигнал, не питание серво.
- Серво получают питание по силовым проводам; земля источника/серво должна быть общей с GND ESP32 для сигнального уровня.
- Цвета проводов у конкретного серво подтвердить по его документации/маркировке, не полагаться только на типовой цвет.
- Breadboard и перемычки должны выдерживать фактический ток; проверить нагрев и просадку питания при старте одного серво и при подключённой камере/Wi-Fi.
- Не соединять выходы двух источников 5V между собой. Не подавать питание обратно в USB-UART/ноутбук.
- Не держать серво в механическом упоре; определить безопасные закрытый/открытый пределы для каждого отсека.

Испытать сначала один серво без нагрузки, затем каждый отсек по отдельности, потом всю систему в последовательном цикле. Следить за reset ESP32, сбоем камеры/Wi-Fi, нагревом и шумом питания. Если появляются сбои, остановиться и пересмотреть питание/проводку до автоматизации.

## 9. Реализация по этапам

### Этап A — проверить железо и pin map

- Сверить camera pin map с предыдущим работающим скетчем и фактической платой.
- Уточнить USB-UART TX/RX логический уровень и COM-порт.
- Подтвердить, что microSD не используется и GPIO12/13/14 подходят фактической плате; GPIO12 проверить на каждом старте.
- Подключать питание/серво по одному и наблюдать за reset, нагревом и работой камеры/Wi-Fi.

### Этап B — прошивка серво без ИИ

- Прошить `esp32_cam/HerbiBioS/HerbiBioS.ino` и проверить `READY`.
- Проверить manual угол каждого сервопривода через сайт без нагрузки.
- Сохранить для каждого BIN реальные CLOSED/OPEN положения через сайт.
- Затем проверить автоматический 3-секундный цикл по одной команде и `BUSY` во время движения.
- Проверить reset, отключение Serial и повтор команды.

### Этап C — локальная обработка фото на ноутбуке

- Запустить ноутбучную панель `python control_panel.py` и проверить localhost.
- Подключиться к точке доступа камеры и проверить JPEG endpoint `/capture`.
- Переиспользовать обученную модель, face suppression, 0.55 threshold и mapping.
- Проверить известные классы, UNKNOWN, лицо, пустое/плохое изображение и низкую уверенность.

### Этап D — связать Wi-Fi, inference и Serial

- Настроить COM-порт/baudrate по конкретному адаптеру.
- Проверить `ACK`, `BUSY`, timeout, reconnect, дубликаты и UNKNOWN.
- Сначала использовать dry-run или отключённые сервоприводы.
- Лишь после проверки всей цепочки включить физические сервоприводы.

### Этап E — испытания макета

- Снять фото каждого класса/предмета с реального положения камеры.
- Проверить освещение, фон, ложные лица/блики, перекрытие, точность коробок и confidence.
- Прогнать каждый отсек многократно, отдельно записать число правильных/ошибочных/пропущенных сортировок.
- При любой небезопасной ошибке отключить actuation и настроить mapping/порог/механику.
- Не заявлять точность физической сортировки, пока не проведены и не записаны реальные испытания.

## 11. Текущие команды ноутбука

Из PowerShell, находясь в `laptop_ai`:

```powershell
python -m pip install -r requirements.txt
python control_panel.py
```

Откройте `http://127.0.0.1:5000`. Сайт запускается только на ноутбуке. Есть ручной режим для управления серво и настройки углов, автоматический режим через ИИ, проверка камеры и превью. Физическое управление отключено по умолчанию и требует явного разрешения в конфиге. Для старого live-просмотра webcam используйте `python predict.py --source 0 --display --device cuda:0`.

```powershell
python main.py
```

Запускает консольный интегрированный режим; для кнопочного управления используйте `python control_panel.py`.

## 12. Решения, ожидающие подтверждения

1. Сверить AI-Thinker camera pin map на этой плате.
2. Подтвердить уровень UART USB-TTL (ESP32 GPIO — 3.3V logic) и COM-порт.
3. Проверить GPIO12/13/14 на отсутствие конфликта; IO12 отдельно проверить при старте ESP32.
4. Проверить реальные положения серво и последовательный трёхсекундный цикл без упора.
5. Проверить `/health` и `/capture` по Wi-Fi AP.
6. Включить физическое управление в конфиге только после прохождения тестов без нагрузки и dry-run.
7. Добавить реальные CAD-файлы корпуса, если они существуют отдельно.

Распиновка и код внесены в `esp32_cam/HerbiBioS/`; следуйте инструкции в `esp32_cam/README.md`. До проверки на физической плате не считать camera pin map, углы серво или последовательный цикл подтверждёнными.
